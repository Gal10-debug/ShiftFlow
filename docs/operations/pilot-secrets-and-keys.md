# Pilot secrets and Data Protection

## Provisioning and access

No real production credentials are generated by this change. Before an approved deployment, the operator provisions unique random credentials (at least 24 characters; 32 random bytes encoded is a practical choice) via a private password manager/terminal that does not log values. Separate credentials are required for PostgreSQL owner, migrator, runtime, backup and initial administrator. Store each value as a file under a 0700 host directory on encrypted storage. Never use dev/demo secrets, repository variables containing passwords, command-line password arguments or `.env` files.

Required files under the config's `secrets` directory:

| File | Content / consumer |
| --- | --- |
| `postgres-owner-password` | New instance owner credential; PostgreSQL only |
| `runtime-password`, `migrator-password`, `backup-password` | Role provisioning inputs; operator script only |
| `runtime-connection` | Runtime connection string; app/bootstrap/maintenance only |
| `migration-connection` | Migrator connection string; migration container only |
| `backup-pgpass` | PostgreSQL pgpass entry; backup container only |
| `bootstrap-password` | Initial admin password; bootstrap container only |
| `keys.pfx`, `keys-password` | Private Data Protection protection certificate and PFX password |
| `tls.crt`, `tls.key` | Trusted TLS certificate chain and private key; proxy only |

Connection format: `Host=postgres;Port=5432;Database=shiftflow_pilot_<id>;Username=sf_<id>_runtime;Password=<provisioned-value>;Maximum Pool Size=20;Timeout=5;Command Timeout=30;SSL Mode=Disable`. Use the migrator role in `migration-connection`. The two files must match the separately provisioned role passwords. `backup-pgpass` uses `postgres:5432:*:sf_<id>_backup:<provisioned-value>`; use appropriately escaped pgpass content if the chosen password contains delimiters. Prefer hex-generated secrets to avoid delimiter mistakes.

`SSL Mode=Disable` is restricted here to PostgreSQL on the private same-host Docker data network. It is not end-to-end database TLS; approve this trust boundary. External database configuration requires `VerifyFull` and trusted server certificates; that alternative topology has not been validated by this package. Do not expose 5432.

Compose file secrets are read-only bind mounts, not an encrypted secret store. On Linux, use separate service groups/ACLs so UID1654 (app), UID101 (proxy) and UID70 (PostgreSQL/backup) can read only their mounted files. Compose local file-secret `uid`/`mode` declarations do not reliably remap host ownership. Validate access on the selected host. The disposable Docker Desktop harness uses 0444 files beneath a host-only 0700 parent to support the three distinct UIDs; that is not a production filesystem policy. The app rejects group/world-writable text secrets and requires an absolute, private key directory. Keep source files unwritable to containers, protect the Docker socket, and remove bootstrap credentials from the operational host after onboarding. Keep provisioning credentials in restricted escrow if needed for recovery.

## Keyring persistence and protection

The app runs as UID1654 with a 0700 named key volume and stable application discriminator `ShiftFlow.Pilot.<deployment-id>`. ASP.NET Data Protection persists XML keys and wraps key material with the provisioned certificate; persistence alone is not encryption. The local drill checks the `encryptedSecret` XML wrapper and authenticates through restart and container replacement with the same cookie. The PFX and password are both required to decrypt keys, so co-locating all secrets does not protect against a fully compromised host. Encrypted disks, restricted host access and encrypted off-host recovery bundles remain deployment gates.

Provision a suitable RSA private certificate with an operator-approved validity/renewal policy; never reuse the web TLS certificate or commit generated material. Certificate validity and private-key presence are checked at startup. The local harness generates only short-lived synthetic certificates. Test certificate loading, permissions and key creation on the final Linux host before onboarding.

Back up the **complete** key directory, PFX, its password, deployment ID and private configuration separately from the SQL archive, encrypted for authorized recovery owners. Keep all old keys required by retained backups. A database dump does not contain the keyring. Snapshot the key volume during a controlled maintenance window with app stopped, using an ownership-verified container/volume and a private encrypted destination; no general-purpose host-volume copy command is supplied because host storage/encryption is undecided. Prove restoration of that bundle on the approved host before live use. The local drill proves persisted-volume continuity, not off-host host-loss recovery.

Data Protection's default key rotation remains enabled. Do not delete retired keys while cookies/backups may depend on them. The current package loads **one** protection certificate. Certificate rotation must be planned: preserve the old decryption certificates, test a reviewed configuration supporting old/new decryption keys before changing the protection certificate, or explicitly invalidate sessions and create a new ring during controlled maintenance. Simply replacing the PFX can make old keys unreadable. Never promise transparent certificate rotation from this single-certificate setup.

If key compromise is suspected, restrict access, preserve evidence, rotate credentials/certificate/keyring through a reviewed recovery procedure and invalidate every Identity security stamp before reopening. Reusing a database snapshot can resurrect old stamps: target-confirmed `invalidate-sessions` is mandatory before exposing restored data even when keys survived.

## Logging and CI

JSON logs contain method, status, elapsed time and server-generated request ID. No HTTP body, cookie, connection string, user identity or full request URL is added by the pilot middleware. EF SQL and framework exception payload logging are suppressed. Do not enable verbose HTTP/EF logging in a live pilot. Existing bounded solver diagnostics are synthetic in CI; treat operational logs as restricted nevertheless.

Docker application/proxy/database logs are capped at 3 × 10 MiB per service. Proposed operational retention is seven days in a restricted destination, subject to owner/privacy approval. The backup operation writes a 0600 archive; private failure diagnostics stay next to private secrets and must never be uploaded. CI publishes only the deployment status report. No CI deployment secrets are needed; the harness generates disposable credentials and cleans its own resources.
